# ForteBank Datathon 26 — ИИ-сервис выявления нарушений кассовой дисциплины по видео

Полностью **локальный** сервис: пользователь (или жюри через API) загружает видеозапись работы кассира, сервис
сообщает, обнаружены ли **признаки** возможных нарушений, и для каждого находит **таймкод**, **кадры-доказательства**,
краткое **описание наблюдаемого** и **норму НБ РК с точным пунктом и дословной цитатой**.
Результат — подсказка для проверяющего, а не юридическое или дисциплинарное заключение.

> Интерфейс и описания нарушений — на казахском языке. Документация — на русском (язык кейса).

## Быстрый старт

Требования: Linux/macOS, Python 3.11+, ~4 ГБ свободного места, **GPU не нужен** (CPU, 8+ потоков желательно).

```bash
python3 -m venv venv && source venv/bin/activate
pip install -r requirements.txt

cp .env.example .env
# сгенерируйте ключ и впишите в .env как API_KEY=...
python -c "import secrets; print(secrets.token_urlsafe(32))"

./scripts/start_server.sh        # http://127.0.0.1:8000
```

Веса моделей лежат в `models/` (YOLOv8m-pose, YOLOv8m, OWLv2). **После их загрузки интернет для обработки видео не нужен**:
скрипт запуска выставляет `HF_HUB_OFFLINE=1`, `TRANSFORMERS_OFFLINE=1`, `YOLO_AUTOINSTALL=False`.
Если каталога `models/` нет, один раз выполните `python scripts/download_models.py` (нужен интернет только для этого шага); вручную:

| Файл | Источник |
|---|---|
| `models/yolov8m-pose.pt`, `models/yolov8m.pt` | https://github.com/ultralytics/assets/releases |
| `models/owlv2-base/` | `google/owlv2-base-patch16-ensemble` (Hugging Face), `save_pretrained("models/owlv2-base")` |

Веб-интерфейс: открыть `http://127.0.0.1:8000`, ввести API-ключ, загрузить видео. Статус обработки (с процентами)
и результат отображаются автоматически.

## Публичный адрес (Cloudflare Tunnel)

Сервис слушает только `127.0.0.1`; наружу он публикуется через туннель (регистрация не нужна):

```bash
# 1) бинарник cloudflared (один раз): https://github.com/cloudflare/cloudflared/releases  -> ~/.local/bin/cloudflared
# 2) терминал A:
./scripts/start_server.sh
# 3) терминал B:
./scripts/start_tunnel.sh        # напечатает https://<имя>.trycloudflare.com
```

Адрес меняется при каждом запуске туннеля; компьютер должен оставаться включённым и подключённым к сети, пока жюри проверяет.

## API для жюри

Заголовок `X-API-Key: <ключ>` обязателен; без верного ключа — `401`. После 10 неудачных попыток за минуту — `429`.

### 1. Загрузить видео
```bash
curl -X POST https://<адрес>/api/v1/analyze -H "X-API-Key: <ключ>" -F "file=@video_017.mov"
# -> 202 {"job_id": "9f3c1a7e5b2d4c60", "status": "processing"}
```
Принимаются `.mov` (основной формат), `.mp4`, `.avi`, `.mkv`; до 200 МБ; содержимое проверяется (сигнатура контейнера,
декодирование, разрешение, длительность ≤ 15 мин).

### 2. Получить статус и результат
```bash
curl https://<адрес>/api/v1/jobs/<job_id> -H "X-API-Key: <ключ>"
```
Ответы: `{"status":"processing","progress":42,"stage":"..."}`, `{"status":"failed","error":"..."}` либо:

```json
{
  "job_id": "9f3c1a7e5b2d4c60",
  "status": "done",
```

## Как это работает

```
видео (.mov) ─► проверка файла ─► очередь (1 воркер) ─► АНАЛИЗ ─► результат (JSON + кадры) ─► UI / API
                                                        │
   1. Люди:   YOLOv8m-pose + ByteTrack, ~2 кадра/с (шаг растёт, если не хватает времени)
   2. Сцена:  кассир = самый долгий человек в помещении; «сидит/стоит» по высоте бокса; зона стола по следу запястий;
              люди за стеклом (мелкие боксы) отбрасываются; интервалы «кассир встал и стол опустел»
   3. Дверь: эталон сцены по первым кадрам; крупная вертикальная область в верхней части кадра, изменившаяся и не
              объяснимая людьми (±1.5 с), держится ≥ 5 с → дверь оставлена открытой
      Экран ноутбука: яркость области экрана (YOLO находит ноутбук) → заблокирован ли ПК при уходе кассира
   4. Предметы:  OWLv2 (открытый словарь) только на кропе зоны стола и только в нужные моменты (≤ 9 проб на видео)
   5. События → нарушения: тип, таймкод, описание «что видно», 1–3 кадра с рамками, норма с дословной цитатой
```

**Почему именно так.** Обучающая выборка маленькая (42 видео, ~20 разных сценариев «норма / нарушение»), а типы нарушений
в разметке не указаны. Универсальный классификатор по агрегатным признакам (число людей, длительность, перемещения…) на
этих данных ничего не различает (leave-one-out ≈ случайное угадывание — проверено, `tools/loo_experiment.py`).
Нарушения оказались конкретными действиями (например, в паре Х-28/Х-29 единственное различие — экран ноутбука заблокирован
или нет), поэтому сервис проверяет **конкретные наблюдаемые состояния**, а не «подозрительность вообще».

**Устойчивость к ракурсу.** Все расстояния и зоны задаются относительно самого кассира (его рост, его место за столом, след
его рук), без привязки к координатам кадра. Обучающая выборка включает несколько разных ракурсов.

**Бюджет времени.** Дедлайн (5 мин) считается от момента получения видео; этап людей получает ≈60 % остатка и автоматически
прореживает кадры, OWL-пробы пропускаются, если времени мало. Самое длинное видео выборки (143 с) обрабатывается ≈75 с.

## Какие нарушения распознаёт сервис

| Тип (в интерфейсе — на казахском) | Что должно быть видно | Норма |
|---|---|---|
| **Дверь кассового помещения оставлена открытой** (`door_open`) | после прохода человека полотно двери не вернулось в исходное (закрытое) положение и держится так ≥ 5 с; люди и смена освещения исключаются | Правила № 14, п. 8 |
| **Кассир пользуется мобильным телефоном** (`phone_use`) | телефон у лица кассира или в его руке (ближе к руке кассира, чем к руке клиента), ≥ 2 раз за 6 с | Правила № 231, п. 12 |
| **Видеокамера закрыта / нет изображения** (`camera_blocked`) | кадр однородный, слишком тёмный или засвеченный ≥ 2 с | Правила № 14, п. 16 пп. 6) |
| **Видеокамера повёрнута или сдвинута** (`camera_moved`) | вся сцена сместилась относительно первых кадров (фазовая корреляция, ≥ 5 % кадра) ≥ 2 с | Правила № 14, п. 16 пп. 6) |
| **Кассир ушёл, оставив клиента** (`left_with_client`) | кассир встал и покинул зону стола, а человек, бывший в помещении ≥ 3 с до этого, остался | Правила № 231, п. 22 (прямая норма) |
| **Посторонний вошёл в отсутствие кассира** (`entered_while_away`) | новый человек появился в помещении, пока рабочее место пусто | Правила № 14, п. 8 |
| **Посторонний в рабочей зоне кассира** (`outsider_near_cashier`) | человек сопоставимого роста ≥ 2 с находится вплотную к кассиру (≤ 0,3 его роста), это не дубль детекции | Правила № 14, п. 8 |
| **Компьютер не заблокирован при уходе кассира** (`pc_unlocked`) | кассир встал, зона стола опустела, экран ноутбука остался «живым» (яркость не упала до заставки) и не гас до ухода | Требования ИБ, п. 71 пп. 9) *(косвенная норма — см. примечание)* |
| **Ценности оставлены на столе** (`valuables_unattended`) | кассир ушёл, а к концу интервала на столе всё ещё видны банкноты / планшет / сумка | Правила № 231, п. 20, п. 22 |
| **Жеке заттар (сумка, верхняя одежда)** (`personal_items`) | у кассира или на его столе видна сумка / верхняя одежда (зелёная инкассаторская сумка не считается) | Правила № 231, п. 12 |
| **Еда / напитки на рабочем месте** (`food_drink`) | на столе кассира видна чашка / бутылка / еда | Правила № 231, п. 12 (личные вещи) |

Всего 11 проверок. Каждая новая проверка добавлялась, только если на 20 «чистых» видео обучающей выборки она даёт **0 ложных срабатываний**; на синтетических примерах каждая подтверждённо срабатывает (`tests/test_services.py::TestExtraChecks`). Сервис выдаёт только то, что подтверждается видимыми признаками, и предпочитает промолчать,
чем выдумать нарушение (кейс: «ложных срабатываний должно быть как можно меньше»).

## Нормативная база

Тексты документов скачаны с adilet.zan.kz (зеркало zakon.uchet.kz) и лежат в `docs/normative/`; **каждая цитата в сервисе
проверяется автотестом** (`tests/test_services.py::test_quotes_exist_in_source_text`) на дословное присутствие в тексте источника.

| Документ | Что использовано |
|---|---|
| [Постановление Правления НБ РК от 29.11.2019 № 231](https://adilet.zan.kz/rus/docs/V1900019680) «Правила осуществления кассовых операций и операций по инкассации банкнот, монет и ценностей…» | **п. 12** (личные вещи — вне кассового узла; допускаются только средства связи без фото/видеофиксации), **п. 20** (деньги на рабочем месте хранятся в закрывающихся на ключ устройствах), **п. 22** («Кассовому работнику не допускается покидать рабочее место до окончания обслуживания клиента») |
| [Постановление Правления НБ РК от 24.02.2020 № 14](https://adilet.zan.kz/rus/docs/V2000020075) «Правила организации охраны и устройства помещений банков…» | **п. 8** («Кассовый узел подлежит изолированию … одним закрывающимся служебным входом») — для открытой двери |
| [Постановление Правления АРРФР от 03.04.2026 № 53](https://adilet.zan.kz/rus/docs/V2600038336) «Требования к обеспечению информационной безопасности банков…» (заменило постановление НБ РК № 48 от 27.03.2018) | п. 71 пп. 9) — автоблокировка рабочей станции при неактивности > 30 минут |

**Принцип сопоставления «правило → нарушение → фрагмент видео».** Для каждого типа события в `app/services/rule_mapper.py`
записано: документ, пункт, дословная цитата, и **пояснение, как норма связана с наблюдаемым**, а также ограничение. В
ответе API это поле `rule`; в интерфейсе оно показывается рядом с кадрами-доказательствами.

Что мы **не** утверждаем: сервис не говорит «нарушен пункт N», а говорит «наблюдается X, что относится к требованию пункта N;
решение принимает проверяющий». Для блокировки ПК прямой нормы в актах НБ РК не найдено — это отражено в примечании к правилу.

## Ограничения и известные ошибки

- **Покрытие.** Сервис ловит только перечисленные выше типы. Из 22 нарушений обучающей выборки (оценка на ней же, поэтому
  завышена) распознаётся 10; **пропуски возможны и вероятны** — нарушения в разметке часто сводятся к тонким
  действиям, которые сервис не различает: порядок передачи денег клиентом/инкассатором, пересчёт «вручную» вместо
  счётной машины, посторонний человек в кассовой зоне, сейф, оставленный открытым.
- **Сейф.** Открыта ли дверь сейфа — не определяется: в выборке сейф часто заслонён сидящим кассиром (проверено).
- **Дверь.** Детектор сравнивает сцену с первыми кадрами: если видео начинается с уже открытой двери, а потом её
  закрывают, закрытое состояние будет принято за «изменение» (возможна ложная тревога); перестановка крупных предметов в
  верхней части кадра тоже может её дать. При другом ракурсе дверь может оказаться вне верхних 55 % кадра — тогда
  нарушение будет пропущено.
- **Посторонние люди.** Роль человека (клиент / инкассатор / посторонний) по видео не определяется, поэтому проверки `entered_while_away` и `outsider_near_cashier` описывают только положение людей; допуск человека в кассовый узел решает проверяющий.
- **Время события.** Таймкод — момент «кассир встал / предмет замечен», а не обязательно момент нарушения; расхождение с
  ручной разметкой на обучающей выборке: медиана ≈ 3 с.
- **ПК.** Блокировка определяется по яркости экрана: тёмная тема, заставка или экран, отвёрнутый от камеры, дают
  неверный результат. Порог подобран на одной модели ноутбука.
- **Предметы.** OWLv2 может принять предмет за другой (кошелёк за банкноты и т. п.); поэтому порог высокий, а одна детекция —
  лишь повод для проверки человеком.
- **Нормативные ссылки.** Редакции документов могут измениться; цитаты соответствуют тексту на момент загрузки
  (`docs/normative/`), проверять актуальность перед использованием в банке.
- **Звук** не используется; **лица не распознаются**.
- **Производительность.** CPU-инференс: одно видео 15–145 с обрабатывается за ~30–80 с; видео обрабатываются по одному.

## Качество на обучающей выборке

Живой пайплайн (без кэша, как в сервисе) прогнан на всех 42 видео обучающей выборки: `python tools/run_batch.py`.
**Важно:** пороги и ограничения подбирались на этих же видео, поэтому оценка **завышена**; на новых видео и под другим
ракурсом результат будет хуже. Проверка на отложенной выборке невозможна: размеченных видео слишком мало.

| Показатель | Значение |
|---|---|
| Видео в выборке | 42 (22 с нарушением, 20 без) |
| Нарушение найдено (TP) | **10 из 22** (Х-15, Х-17, Х-24, Х-26, Х-28, Х-30, Х-32, Х-33, Х-40, Х-46) |
| Ложные срабатывания (FP) | **0 из 20** |
| Пропущено (FN) | **12 из 22** |
| Точность вердикта по видео | 0.71 |
| Таймкод: расхождение с ручной меткой (только найденные) | медиана ≈ 3 с (1.5 – 9 с) |
| Время обработки одного видео | в среднем ≈ 40 с, максимум 141 с (лимит 300 с); 5 видео одновременно — последнее готово через 240 с |

Сервис выбран **консервативным**: он заявляет нарушение только при видимом подтверждении, поэтому пропускает многое, но
почти не выдумывает. Это сознательный компромисс (в кейсе ложные срабатывания нежелательны); пропуск нарушения, наоборот,
«недопустим», поэтому главный путь развития — расширение набора проверяемых действий (см. ниже).

### Устойчивость к другому ракурсу (критерий 5)
Проверено на изменённых копиях видео (`tools/robust_eval.py`): зеркальное отражение, поворот камеры на 8°, кадрирование
с увеличением влево и вправо — 8 видео × 4 искажения = 28 прогонов. **Вердикт совпал с исходным в 27 из 28.** Единственное
расхождение — Х-32 при кадрировании вправо: дверь вышла за пределы кадра, поэтому «открытая дверь» не видна (ожидаемо).
Ложных срабатываний на искажённых «чистых» видео нет.

### Что даст рост качества (план развития)
1. Классификатор действий по клипам (X3D / VideoMAE, лицензии Apache-2.0/CC) на размеченных по типам фрагментах — для
   пересчёта денег, передачи через лоток, действий с сейфом.
2. Определение роли человека (клиент / инкассатор / посторонний) по траектории входа и положению относительно стола.
3. Дообучение детектора на собственных съёмках (банкноты, сейф, лоток, бейдж) — разрешено ТЗ (FAQ №7).
4. Нормализация ракурса (гомография по углам стола) для устойчивости к смене камеры.

## Безопасность и приватность

- **Доступ к API** — только по `X-API-Key` (сравнение за постоянное время, fail-closed: пустой/шаблонный ключ = всё отклоняется);
  защита от перебора — 10 неудачных попыток за минуту → `429`.
- **Загрузка файлов:** проверка расширения, сигнатуры контейнера, декодирования, разрешения и длительности; потоковая запись с
  лимитом размера; имя файла из запроса в путь не попадает (случайное имя) — защита от path traversal.
- **Приватность:** загруженное видео **удаляется сразу после обработки**; в БД остаются только результат и кадры-доказательства, они **удаляются через 48 часов** (`JOB_RETENTION_HOURS`).
  Осиротевшие файлы старше суток удаляются при старте. Видео не передаётся третьим лицам и не используется для обучения.
- **Идентификаторы задач** — 16 случайных hex-символов; ответ при ошибке не раскрывает пути и трассировки.
- **Веб:** CSP (`script-src 'self'`), `X-Frame-Options: DENY`, `nosniff`, `no-referrer`; нет внешних CDN и шрифтов; описание API
  (`/docs`) отключено; все данные из ответов выводятся с экранированием.
- **Локальность:** обращений к облачным AI-сервисам нет; после загрузки весов интернет для обработки не нужен
  (`HF_HUB_OFFLINE=1`, `TRANSFORMERS_OFFLINE=1`).
- Сервис слушает `127.0.0.1`; наружу — только через туннель. Ключ не хранится в коде и в репозитории (`.env` в `.gitignore`).
- `bandit` по `app/` — без замечаний; `pip-audit` по `requirements.txt` — известных уязвимостей нет.

## Тесты и проверки

```bash
pip install -r requirements-dev.txt
python -m pytest tests -q            # 60+ тестов: API, безопасность, поведение, правила, цитаты норм
python tools/run_batch.py            # живой прогон по обучающей выборке (нужны data/open/…)
bandit -r app && pip-audit -r requirements.txt --no-deps --disable-pip
```
Тесты изолированы: временная БД и ключ, нейросети заменены заглушкой. Отдельный тест сверяет **каждую цитату нормы** с
сохранённым текстом документа.
